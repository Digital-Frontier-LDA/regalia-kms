# Software lab trust boundaries and secret inventory

This is a scoped starting point for #60, not approval of the production threat
model or completion of its secret-lifecycle gate. It authorizes disposable
software experiments only. Production design remains gated by the architecture
decisions recorded in #59 and #60.

## Boundaries

The developer, Docker host/VM, image, and single Python harness are trusted.
Target and authorizing logic run in separate processes, but there is no OS or
operator trust separation: all share the same container UID and trusted harness.
The harness controls the software TPM state and can copy, reset, or inspect it.
Passing these tests provides no physical tamper resistance, anti-cloning, secure
boot, offline theft resistance, rollback-resistant storage, or independence
from a compromised host. Resettable software PCRs are not real measurements.

The tested adversarial inputs are replayed/wrong challenges, substituted public
identity/session fields, modified quoted data, changed PCR state, foreign sealed
objects, wrong/missing LUKS factors, and a removed LUKS path. Separate verifiers
also enforce fixture policy states/current epoch, quote PCR selection, challenge
expiry and single-use state, authenticated session-encrypted responses, and
bounded strict IPC parsing. Concurrent workers share a lock and atomically
replace state before issuing a response. A negative test is
accepted only after the corresponding positive case is exercised. TPM policy,
authentication, and integrity refusals require the expected TPM error code;
LUKS credential refusals require exit 2, rather than arbitrary tool failure.

Docker runs with no network, published ports, devices, extra capabilities, host
TPM sockets, host disks, or Docker socket. `/tmp` is a private tmpfs and only the
sanitized evidence directory is bind-mounted. This reduces accidental access
to unrelated work; it is not a security boundary against the developer or
Docker host. Host memory capture, swap, VM snapshots, and crash collection remain
outside the claims of this lab.

Native runs also enable swtpm's own syscall filter. Architecture translation on
this Docker VM requires disabling that additional filter, with the exception
recorded in evidence. Docker's default seccomp policy, non-root execution, dropped
capabilities, no-new-privileges, network isolation, and read-only root remain in
force. The software TPM is a trusted lab tool in both cases.

## Lab secret lifecycles

All values are disposable test material. Only the harness may generate/use them;
there is no production recovery credential or existing device credential involved.

| Material | Generation and storage | Rotation / revocation / recovery |
|---|---|---|
| Software TPM hierarchy seeds, EK, AK, storage parent | New swtpm state per run in tmpfs; keys created with tpm2-tools; public AK used for verifier pinning | Discard on exit; new identities each run; no persistent recovery |
| Local LUKS contribution | 32 random bytes generated by harness, sealed to TPM-A PCR policy; plaintext also remains in Python memory | New per run; future unseal denied by changed PCR; discard on exit |
| Peer B/C contributions | Two independent 32-byte secrets generated by each verifier process; private software state in tmpfs; delivered via signed RSA-OAEP responses | New per run; capability/epoch/challenge checks govern release; remove keyslot for path-removal test; discard on exit |
| Verifier Ed25519 signing keys | Each verifier generates its own software key in private tmpfs state; harness pins only the public key for response verification | New per run; no production identity, hardware custody, or independent operator boundary |
| Derived LUKS credentials | Established HKDF-SHA256 over two fixed-length contributions with target/peer domain separation; memory, stdin, briefly a private tmpfs file for adding the second slot | Remove B slot in test; temporary key file unlinked; all state discarded on exit |
| LUKS volume key | cryptsetup creates a real encrypted test header/image in tmpfs | No backups or recovery slot; discard image on exit |
| Boot WireGuard private key | `wg genkey`; sealed to TPM-A PCR policy, also present in harness memory/stdin | New per run; changed PCR blocks fresh unseal; no interface or remote peer configured |
| Boot-session private keys | cryptography library generates transient RSA-3072 keys for the peer response profile; generic transcript tests also use X25519 public-key fixtures | New per boot fixture; RSA private key decrypts only session-bound responses; first valid response consumes the software session; discard on exit |
| Nonces/session IDs | OS randomness; transient request fixture and tool input | Fresh per attempt; old quote fails under new challenge |
| Pending challenges | Random IDs/nonces and monotonic expiry in private verifier state; max 16 pending entries | Pruned after expiry; owned attempt consumed before verification/response work; atomically persisted for process-level replay protection |

Policy state and challenges are ordinary tmpfs files. They are not a durable TPM
epoch/high-water store and provide no anti-rollback against the Docker host.
Fixture policy changes are injected by the trusted harness. Consuming a challenge
before verification can deny that attempt after a forged/lost message; a new
challenge is required. Production transport identity, replay journals, policy
freshness, and availability under malicious traffic still require qualification.

TPM-sealed blobs and context files are readable by the harness and software TPM
host. They are not evidence that a real stolen TPM resists extraction. Python
immutable buffers are not explicitly zeroized/locked; process termination and
tmpfs teardown are the cleanup mechanism. No raw secrets are written to evidence
or logs; errors deliberately omit captured tool stdout because unseal returns
plaintext there.

## Production lifecycle decisions still required

| Inventory group | Required production decisions |
|---|---|
| LUKS local/per-peer contributions and recovery secrets | Generation/custody, recipient binding, independent rotation, keyslot/header backup policy, recovery authority |
| TPM identity/sealing keys and epoch high-water state | Physical enrollment, PCR/event-log coverage, policy authorization, TPM NV wear/crash behavior, TPM clear/replacement handling |
| Boot/runtime WireGuard keys | Distinct planes, endpoint/firewall configuration, PCR binding, rollover, revocation, network-source availability |
| HSM User PIN and SO PIN; DKEK; service private keys | Reconcile static PIN versus PKA, SO-PIN reset protections, online exclusions, ceremony custody, physical device qualification, homogeneous/heterogeneous recovery |
| YubiKey operational PIN, admin credentials, PUK | OpenPGP/PIV independence, bounded PIN lifetime, retry protection, admin/PUK exclusion, lost-token recovery, TPM-free profile limitations |
| Membership root and restrictive revocation signer | Signed representation, signer roles, monotonic epochs, conflicting updates, root rotation, stale-authorizing-peer policy |
| Runtime service keys/certificates and lease signers | External expiry enforcement, authenticated time, root-compromise limits, independent single-signer fencing, partition policy |

No production enrollment/PKA/hardware-custody decision is changed by this lab.
Immediate global revocation cannot be inferred from asynchronous manifests.
Any-node bootstrap eligibility does not grant permission for simultaneous KMS
signers under the existing `FENCING.md` contract. Pico software/staging results do
not qualify Nitrokey or heterogeneous production key domains.

## Network and guest extensions

The [network lab](NETWORK.md) separates three process/container identities and
private state stores, while trusting the shared Docker host and fixture controller.
Namespace setup requires limited network/user capabilities; services and software
TPMs run as UID 10000 with no effective capabilities. Temporary recovery
credentials exist in host controller memory for actual keyslot verification.

The [guest lab](VM.md) passes only the disposable virtual TPM, encrypted image,
public initramfs and userspace network into QEMU. The commissioning fixture
temporarily caches existing local plaintext factors before surveying firmware
PCRs, reseals those same factors to the observed guest baseline, and drops those
references. These local controls are lab-only and never exposed by the bootstrap
endpoint. The guest's private recipient key and unsealed values live in guest RAM
and pipes. No guest recovery credential or peer private factor is packaged in the
initramfs. Software TPM permanent state survives backend restarts but remains
cloneable/rollbackable by the trusted host. Neither extension supplies hardware
custody, secure zeroization, signed membership freshness, or qualified early-code
measurements. Their limitation scenarios are observations, not production passes.
