# Three-site KMS: secret inventory and lifecycles (Phase 0, #60)

Every secret the three-site design (#59) uses, with its generation, storage, exportability,
authorized use, rotation, revocation, recovery and **custody role**. Companion to
[THREE-SITE-THREAT-MODEL.md](THREE-SITE-THREAT-MODEL.md). Secrets marked *existing* are already in
use; *proposed* ones belong to a phase and do not exist until it lands.

Custody roles: **Owner** (the principal; sole shareholder); **Technical director** (reaches the
datacenter tokens, never the PINs); **Shareholders** (k-of-n case holders); **Node** (the machine
itself, no human); **Fencing authority** (independent activation signer, FENCING.md).

## Disk unlock (Phases 6–7, 11)

**LUKS2 volume key** (per node, proposed in this form; LUKS itself existing)
- Generated by `cryptsetup luksFormat` on the node; never leaves the LUKS header, where each keyslot
  wraps it under one credential.
- Not exportable except as header + a keyslot credential; header backups are ciphertext.
- Use: dm-crypt at boot. Rotation: `cryptsetup reencrypt` (rare; on suspected exposure).
- Revocation: not applicable (rotate). Recovery: through the recovery keyslot below. Custody: Node.

**Local TPM contribution** (per node, proposed)
- 256-bit random, generated on the node, sealed to its TPM under the measured-boot policy (#65).
- Not exportable (TPM-sealed, `fixedTPM`). Use: one input to every peer-path keyslot credential.
- Rotation: with a measured-policy change (#75) or on node replacement. Revocation: TPM clear /
  node retirement. Recovery: not recoverable by design; the recovery keyslot covers loss.
  Custody: Node.

**Peer contribution, per (target, peer) pair** (proposed: `B→A`, `C→A`, and so on, six in all)
- 256-bit random, generated by the peer for that target at enrollment, stored only inside the peer's
  own encrypted root (so a powered-off peer yields nothing).
- Not exportable outside the bootstrap protocol: sent only encrypted to a target's freshly attested
  ephemeral key, and only when the target is ACTIVE/MAINTENANCE in a fresh manifest.
- Use: `credential = HKDF-SHA256(ikm = local || peer, info = "regalia/luks/v1/<target>/<peer>/<path epoch>")`
  opens that pair's keyslot. Neither input alone opens anything (S1).
- Rotation: per pair, independently (new contribution + new keyslot, old keyslot killed).
- Revocation: kill the pair's keyslot on the target; peers drop contributions for revoked targets.
- Recovery: re-enroll the pair. Custody: Node (the peer).

**Recovery keyslot credential** (per node, proposed; resolves "one manual recovery", A3)
- High-entropy (≥ 128-bit) passphrase, generated offline at enrollment.
- Stored on paper in the Owner's safe (like the PIN card, its own sealed envelope) and escrowed
  encrypted to the ceremony's breakglass recipient, so loss of the safe is recoverable through k
  shares (ADR-0002 D19: extend under the ceremony roots, no new split).
- Use: only for a total outage (A3) or a node with no healthy peer; one node, then A1/A2.
- Rotation: after every use. Revocation: kill the keyslot. Custody: Owner.

## Attestation and networking (Phases 5–6)

**TPM endorsement key (EK)** (existing): manufacturer-generated, permanent, certificate presence
recorded at intake. Not exportable. Use: anchors the attestation key. Custody: Node.

**Attestation key (AK)** (proposed): generated in the TPM, bound to the EK by credential activation
(MakeCredential/ActivateCredential); restricted signing key, `fixedTPM`. Use: quotes over PCRs bound
to node ID, manifest epoch, boot session, ephemeral key and peer nonce (S3). Rotation: node
replacement. Revocation: membership (the manifest lists each node's AK). Custody: Node.

**WG-BOOT key pair** (per node, proposed): generated in the initramfs build at enrollment, private
half sealed to the TPM under the boot policy. Use: only the peer bootstrap endpoints, before root;
removed after boot. Rotation: with the boot policy. Revocation: manifest + peers' WireGuard peer
lists. Custody: Node.

**WG-SERVICE key pair** (per node, proposed): generated on the node, stored in the encrypted root.
Use: the service plane after boot (peer traffic, optional admin SSH). Rotation: yearly or on
suspicion. Revocation: manifest + peer lists. Custody: Node.

**Boot-session ephemeral key** (per boot, proposed): generated in the initramfs, never stored;
destroyed with the bootstrap buffers after unlock. Custody: Node (RAM only).

## Membership and authority (Phases 8–9, 14)

**Membership root signing key** (proposed): offline Ed25519, generated in a ceremony-grade
session, kept offline under the ceremony custody (its backup wrapped under the ceremony roots, D19).
Use: enroll, replace, change identities, restore trust: every *permissive* transition.
Rotation: rare, with a signed hand-over manifest. Custody: Owner (offline).

**Revocation authority key** (proposed): Ed25519, kept on an accessible but separate host (or an
HSM key). Use: *restrictive* transitions only (QUARANTINED, RETIRED, REVOKED_STOLEN) and freshness
heartbeats; it cannot enroll or activate. Rotation: by a manifest from the root. Custody: Owner.

**Highest accepted epoch** (state, proposed): a TPM NV counter per node, outside restorable disk
state. Custody: Node.

**Fencing authority key** (existing, FENCING.md): Ed25519, held by `regalia-fence` on an
independently administered host; issues activation leases, never overlapping across sites.
Unchanged by this program: bootstrap membership is not activation authority (S4).

**Commissioning evidence key** (existing, `deploy/baremetal/evidence.py`): ECDSA P-256 offline key;
signs each node's commissioning evidence; trusted by recorded fingerprint. Custody: Owner.

## Hardware credentials (existing; Phases 2–4, 12–13 may change the user-PIN line)

**HSM user PIN**: static, generated or chosen at the ceremony, on the PIN card (Owner's safe),
TPM-sealed per host as a systemd credential, escrowed (MAC-authenticated, encrypted to breakglass).
PKA (#63) would replace its *unattended* use only after a recorded decision (ADR-0002 D4 today: no
runtime PKA).

**HSM SO-PIN, YubiKey PUK and management key**: generated at the ceremony, only in the tier-0
payload (k shares). Never online, never in a bootstrap bundle (S5).

**YubiKey PIV PIN**: as the HSM user PIN (TPM-sealed, PIN card, escrow).

**DKEK and its k-of-n shares**: ceremony-generated; shares in the sealed cases (Shareholders).
Recovery of HSM keys only; separate from disk unlock (#64 tests portability).

**KMS service private keys**: generated in the HSM, non-exportable; backups DKEK-wrapped (D19).

**Breakglass key, escrow MAC key, PIN escrows**: ceremony roots and their extensions, unchanged.

## Service trust (Phase 14)

**Service TLS certificates**: short-lived, issued to the TPM-held TLS key after attestation;
expiry is a control in itself. **Peer runtime leases**: proposed in #74; must be issued by an
independent authority, never self-issued by bootstrap peers.

## Open items this inventory leaves to the phases

- Freshness bound value and heartbeat transport (#69).
- Exact PCR set for the local TPM contribution and the WG-BOOT key (#65).
- Whether the recovery keyslot is per node (proposed) or per cluster (one envelope, more blast radius).
