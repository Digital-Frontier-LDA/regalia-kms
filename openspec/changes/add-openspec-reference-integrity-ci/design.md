## Goals / Non-Goals

The required CI result covers strict syntax, executable checker regressions and reference integrity for the declared snapshot. It retains the existing evidence boundary for prior, proposed, related and opaque inputs. Discovery closure, authority for evidence or N/A, legacy-budget and case-deletion preservation, public source-change comparison, provider settings and commissioning decisions stay outside this design.

## Decisions

### Keep the checker CLI explicit

The current parser inherits argparse's abbreviation support. In the three-option parser a unique prefix such as --snap, --source-rep or --source-rev can satisfy its option. The two source options make --source-re ambiguous. This was independently checked with an inert parser matching the declarations. Recommend setting allow_abbrev=False before installing CI so new option names cannot change the meaning of a prefix. Preserve full long names, the usual long-option value syntax, and -h/--help. Test the entrypoint channels separately. Required-option problems use argparse usage and exit 2. Expected malformed input and reference refusals use JSON and exit 1 after parsing. Help uses text and exit 0 without input reads. Diagnostic wording can vary by Python version. [Python argparse option matching](https://docs.python.org/3.14/library/argparse.html#allow-abbrev).

The checker compares scenario ownership by exact requirement and keeps baseline, related, context and proposed references in distinct groups. Product blobs are loaded only by the local Git reader at the explicitly supplied commit. Candidate inputs must match their current record hash and scope, and a typed external input must match the registry and local cache bytes. Hashing historical record pointers does not authenticate their contents as evidence. Keep the existing JSON envelope and do not treat coverageComplete false as a failing result. [External source data boundary](../../coverage/external-sources/README.md).

### Prepare the product objects before invoking the checker

Keep the canonical workflow checkout as the snapshot. At the end of the existing build-test steps, add a second use of the already pinned checkout action at 3d3c42e5aac5ba805825da76410c181273ba90b1. Fetch the base repository selection from github.repository at the literal product commit using fetch-depth 1, no tags, no LFS or submodules, no sparse/partial filter, and persist-credentials false. Use a reserved unused workspace-relative directory such as .openspec-product-source. Verify it was not occupied in the workflow tree before checkout and require an actual Git checkout. Putting this at the tail avoids affecting earlier whole-tree builds and test discovery. The default workflow token's existing contents read scope is sufficient for same-repository preparation, subject to hosted confirmation. [Pinned checkout inputs](https://github.com/actions/checkout/blob/3d3c42e5aac5ba805825da76410c181273ba90b1/action.yml).

Validate locally that the separate checkout's HEAD is the exact commit and that it resolves as a commit with the expected product tree; require the original workspace HEAD to remain the workflow revision. Run preflight Git with lazy fetch, replacement objects, prompts and transports disabled, matching the checker boundary. Run the checker with the original workspace as --snapshot and the separate directory as --source-repo. No source phase may substitute the workflow head, a branch tip, a remote content URL or a partial object cache. A missing commit or blob is a failure. Full history on the primary checkout would broaden the fetch and still would not provide an explicit independent source boundary. A separate checkout does materialize the pinned tree, but limits Git history and keeps credentials out of the reader.

Verify their exact versions before use. The installed and official OpenSpec 2.1.1 metadata agree on Node >=22.20.0. The inspected installed dependency metadata is consistent with Node 24. ### Run and prove the required commands inside build-test

Use stable step identifiers and fail-fast Bash with pipefail. After source and toolchain checks, invoke the pinned OpenSpec CLI with validate --all --strict --no-interactive --json. Run stdlib unittest discovery with pattern test_check_openspec_references.py and invoke the checker with the three exact full options. Isolate runtime caches and configuration and disable OpenSpec telemetry for this step. Collect the strict result and checker JSON while propagating the real process status. Do not add a condition or continue-on-error that can turn a required check into a skip or success. Keep the aggregate's existing build-test dependency and job count.

Add a wiring regression using the existing YAML structural test layer. It must read the real workflow, find the named steps in the existing build-test job, assert their required order, immutable refs, command arguments and failure policies, and verify build-test stays in the aggregate dependencies. Exercise the actual check step's extracted shell body with inert command doubles: each phase independently fails in one arm, and an all-success arm returns zero with the expected invocation trace. Real OpenSpec and checker negative fixtures should separately fail for invalid spec, bad reference and malformed schema. Mutants removing strict validation, swallowing reference status, or replacing the literal pin must be caught by the intended wiring checks. Fresh baseline, no-op and restored copies must pass.

## Risks / Trade-offs

- An unavailable exact Git object or registry package fails the job. Keep the declared pin, report the specific preparation failure, and avoid silently substituting current sources or unpinned tooling.
- The existing job has a 20-minute budget. Fetch and install startup adds time, so collect step durations in the first exact-head run and fix measurable overrun before acceptance.
- The CLI checks declared relationships, not ledger completeness or evidence semantics. Logs should record both fixed boundary fields and avoid labels suggesting verified coverage.
- Main and baseline delta remain paired inputs of the current checker. Keep this change separate. A later archive or sync that adds tooling requirements to the baseline needs its own coordinated main/delta and authoring reconciliation.

## Migration Plan

Review the inactive plan first. Then land the parser and tests, preparation and pins, and the wiring inside build-test under the authorized implementation round. Require a hosted run whose evaluated revision, job and attempt are bound to its exact change, plus intended negative controls. Any rollback is a reviewed revert of this finite CI wiring. The local helper and existing gate/forge policies are separate.
